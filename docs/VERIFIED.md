# Verified S3 behaviors

CloudVault is a functional simulation of Amazon S3 (doc 15, AM-7). This file records the real S3 behaviors the simulation copies, each checked against the official AWS documentation. No AWS account was used. "Simulation" says how CloudVault reproduces the behavior.

Checked on 2026-10-05.

| # | Behavior | Finding (AWS documentation) | Simulation | Source |
|---|---|---|---|---|
| 1 | Plain delete on a versioned bucket | Confirmed. "A simple DELETE cannot permanently delete an object... Amazon S3 inserts a delete marker in the bucket, and that marker becomes the current version of the object with a new ID." A plain delete when the current version is already a marker adds another marker. | `delete_object` adds a marker row with a new version id and returns it; it never removes data | [Deleting object versions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html), [Managing delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html) |
| 2 | Delete by version id; undelete | Confirmed. "To delete versioned objects permanently, you must use DELETE Object versionId." Deleting the current delete marker by its version id makes the previous version current ("To undelete the object, you must delete this delete marker"). | `delete_version` removes exactly that row; the latest remaining row becomes current | Same as row 1 |
| 3 | GET/HEAD of a deleted object | Confirmed. Without a version id, when the current version is a delete marker: 404 Not Found with `x-amz-delete-marker: true`. With a version id that names a delete marker: 405 Method Not Allowed with `x-amz-delete-marker: true` and `Last-Modified`. | `head_object`/`get_object` raise `NoSuchKey` (404) and `MethodNotAllowed` (405) for these cases | [Working with delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeleteMarker.html), [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) |
| 4 | Copy in a versioned bucket | Confirmed. The copy source defaults to the current version; `versionId` selects another one. "Amazon S3 generates a unique version ID for the copied object," returned in `x-amz-version-id`. `x-amz-storage-class` can be set on the copy ("You can use the CopyObject action to change the storage class of an object"). **If no storage class is given, the copy is stored as STANDARD.** Tags are copied by default (`x-amz-tagging-directive` defaults to `COPY`). | `copy_object(key, source_version_id, storage_class)` creates a new version row with a new id, copies data, metadata and tags, and uses STANDARD unless a class is given. Restore therefore produces a STANDARD version; Apply passes the target class | [CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html) |
| 5 | HEAD and the storage class | Confirmed. `x-amz-storage-class`: "Amazon S3 returns this header for all objects except for S3 Standard storage class objects." | `head_object` returns `storage_class=None` for STANDARD; the Inspector shows "STANDARD" when it is absent | [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) |
| 6 | ETag | Confirmed. Objects created by PUT or Copy and stored as plaintext or SSE-S3 "have ETags that are an MD5 digest of their object data"; not for SSE-KMS/SSE-C or multipart. | ETag = quoted hex MD5 of the bytes (no multipart, no KMS in scope) | [Object data type](https://docs.aws.amazon.com/AmazonS3/latest/API/API_Object.html) |
| 7 | Upload checksum | Partly confirmed. S3 "independently calculates a checksum value of the object on the server-side, and validates it with the provided value before storing the object and checksum value." SHA-256 is a supported algorithm and is returned base64-encoded (`x-amz-checksum-sha256`). The exact error code for a mismatch was not shown on the pages read. | `put_object` recomputes SHA-256 and rejects a mismatch with `BadDigest` before storing; checksum stored base64-encoded | [Checking object integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html), [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) |
| 8 | Presigned URL expiry | Partly confirmed. A presigned URL can be used multiple times "up to the expiration date and time"; "Amazon S3 checks the expiration date and time of a signed URL at the time of the HTTP request", and after expiry the download fails. Presigned URLs "are bearer tokens that grant access to those who possess them." The pages read describe refused presigned requests as 403 Forbidden / AccessDenied but do not name the exact code for expiry. | Signed link checked at request time; expired, altered or missing signature returns 403 `ACCESS_DENIED`; anyone holding a valid link can use it until it expires | [Download and upload objects with presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html), [Sharing objects with presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html) |
| 9 | Lifecycle: noncurrent expiry and expired delete markers | Confirmed. `NoncurrentVersionExpiration` removes noncurrent versions a number of days "after they become noncurrent". "A delete marker with zero noncurrent versions is referred to as an expired object delete marker"; `ExpiredObjectDeleteMarker` removes it. The AWS example puts `ExpiredObjectDeleteMarker` and `NoncurrentVersionExpiration` in the same rule (it cannot be combined with `Days` in one rule). | Lifecycle script: a version is noncurrent from the `last_modified` of the next newer version of the same key; expires 90 days later; then markers with no versions behind them are removed | [Lifecycle configuration examples](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-configuration-examples.html), [Managing delete markers](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ManagingDelMarkers.html) |
| 10 | Storage-class minimums (engine thresholds) | Confirmed. STANDARD_IA: minimum storage duration 30 days, minimum billable object size 128 KB, per-GB retrieval fees. GLACIER_IR: 90 days, 128 KB, millisecond access, per-GB retrieval fees. STANDARD: no minimums. | The doc 07.2 thresholds (`REC_MIN_SIZE`=128 KiB, 30 and 90 days) follow these values. The simulation stores the class; it does not bill | [Storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html) |
| 11 | Object tags | Confirmed. Up to 10 tags per object, unique keys; key up to 128 Unicode characters, value up to 256. | CloudVault writes only 2 tags (`project`, `env`); the store rejects more than 10 tags or longer keys/values | [Tagging your objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-tagging.html) |
| 12 | Free database tier (sizing) | Neon Free plan: 1 GB of Postgres storage per project (raised from 0.5 GB on 2026-10-02), 20 GB across projects. | `SIM_STORAGE_LIMIT_BYTES` default 300 MiB leaves room for application tables, indexes and Postgres overhead | [Neon Free plan limits](https://neon.com/faqs/free-plan-limits-and-quotas), [Neon changelog 2026-10-02](https://neon.com/docs/changelog/2026-10-02) |

## Not verified, not relied on

- Copying an object onto itself with no changes. The AWS docs read do not state this rule. CloudVault never needs it: Apply always changes the class, and restore copies an older version, not the current one.
- Exact error code names for a checksum mismatch and an expired presigned URL (rows 7 and 8). CloudVault uses its own codes from doc 15 for its API.
